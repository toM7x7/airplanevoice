# 「見惚れる飛行」— 体験品質の企画・仕様 v0.2

更新: 2026-09-16 / 対象: v0.8.0からv0.8.1への品質改善

**状態: ユーザーの実装依頼を受け、光・材質・コード生成の機体をv0.8.1で改善。PCの比較確認まで実施し、Quest実機での品質評価は未確認。** 第2節は改善前の調査記録。第10節へ実装した範囲と残りを記録する。共有版QR入室・共有・同期の実機成功報告は受領したが、光・形・負荷の個別評価とは分ける。

## 1. 目指す体験

> 地上から見上げた一機に、自然と目が留まる。光を受けて変わる形を追い、遅れて届く音を聴き、通り過ぎたあとも、もう少しその空にいたくなる。

「見惚れる」はユーザーが重視すると確認した品質目標。太陽に照らされた側面の美しさ、旅客機の存在感、気持ちよい音を育てる。改善候補の採用は、実際の観察位置で見える・聞こえることを確かめて決める。

### 体験の流れとして見る4つの瞬間

| 瞬間 | 起きてほしいこと | 観察する点 |
| --- | --- | --- |
| 気づく | 音や動く輪郭に気づき、自分で空を見回す | 強制的な視線移動や説明がなくても探せるか |
| 見つける | 翼・胴体・エンジンの関係が見え、旅客機として捉えられる | 通常の距離・倍率で外形が読めるか |
| 見惚れる | 滑らかな移動と、曲面を移る光をしばらく追いたくなる | 眩しさ・点滅・小刻みな姿勢変化で注意が途切れないか |
| 余韻を味わう | 遠ざかる機体と、あとから届く音を見送る | 音切れ、急な消失、操作盤や字幕の割り込みがないか |

順番を固定した演目や、ユーザーが組む新しい制作工程にはしない。見えてから音を待つ場合も、音から探す場合も成立させる。手動で作った航路でも魅力が残るかを確かめる。

## 3. 「作ったのに見えない」を先に切り分ける

改善前に、対象が次のどこで失われるか確認する。

1. **状態**：飛行中か、細部の非表示条件に入っていないか。
2. **視界・遮蔽**：視野外、機体の裏側、風景・操作盤の背後になっていないか。頭やカメラを動かすと見えるか。
3. **画面内の大きさ**：機体・対象部品が何画素程度を占めるか。ほぼ1画素以下の模様が、動くとちらついていないか。
4. **光と背景**：形はあるが、空と同じ明るさ・色、白飛び、暗い面のつぶれで読めなくなっていないか。
5. **時間**：目で捉える前に通過する、光沢が瞬間だけ現れる、細部切り替えで途切れるなどがないか。
6. **端末**：片眼だけ、視野の周辺だけ、解像度や描画負荷の条件によって失われていないか。

### 距離による見かけの大きさの例

71mの全長を真横から、視線に対して垂直に見る理想条件の角度。実際には向き・翼・投影・遮蔽により変わる。現行航路の最接近距離を測った表ではない。

| 観察距離 | 全長71mが占める角度 | 高さ0.84mの窓が占める角度 |
| --- | --- | --- |
| 250m | 約16.16° | 約0.193° |
| 1,000m | 約4.07° | 約0.048° |
| 2,000m | 約2.03° | 約0.024° |

計算は`2 × atan(大きさ / (2 × 距離))`。これは幾何学的な例で、Questの視認限界や実効解像度を示す値ではない。

**通常の観察距離では、輪郭・大きな曲面の明暗・ゆっくり動く光沢を優先する。** 窓や小部品への工数は、その違いが実際に届く距離を確認して決める。近接プレビューの美しさと、地上から眺める美しさをそれぞれ評価する。

## 4. 最初の改善仕様案

初回の中心は **「光の整合と、胴体・翼の面が読める質感」**。以下の数値・実装方法は開発側の提案で、採用済みの完成仕様ではない。

| ID | 仕様案 | 確かめ方 |
| --- | --- | --- |
| Q-01 光をそろえる | 太陽の方向・色・強さを一つの設定から空と機体照明へ渡す | 同じ場所で午前風／高い太陽／低い太陽を比較。空と機体の明るい面が整合する |
| Q-02 曲面を光で読む | 空と地面を表した軽量な環境反射を候補にし、塗装・金属・ガラスの粗さを分ける | 旋回や視点移動で光の帯が滑らかに動く。白飛びで胴体と翼の境界が消えない |
| Q-03 通常距離で形を読む | 機首、主翼断面、翼の付け根、エンジンの外形・吸気口を優先して整える | 正面斜め・側面・下方から見て、輪郭と面のつながりが分かる。寸法変更時にも破綻しない |
| Q-04 ちらつきを抑える | 小さな窓・光沢・翼端灯の遠距離での表現と、細部を切り替える条件を調整する | 静止画に加え、飛行中・頭を動かしたとき・境界往復を両眼で確認 |
| Q-05 空から浮かび上がる | 空の明暗、地平線、霞を調整し、明るい胴体・暗い下面の両方を読みやすくする | 晴天・曇天の比較条件で、マーカーを出さなくても機体を追えるか。霞で遠近は残るか |
| Q-06 観察を続けられる | 空間操作盤を視界から外しやすくし、軌跡・選択マーク・字幕の量を選べる方向で設計 | 表示あり／控えめの両方で、機体を追う邪魔にならず必要な操作へ戻れる |
| Q-07 音で見送れる | 観測位置に応じた接近・通過・遠ざかりの響きを連続させる。方向と到来時刻は保つ | 同じ音量で比較し、厚み・方向の分かりやすさ・聞き疲れをQuest本体スピーカーで確認 |

### 「輝く」の扱い

狙うのは、太陽と視点の関係で胴体や翼の輝きが変わること。機体全体を常時発光させたり、点滅粒子を追加したりする仕様にはしない。強い光のにじみ、雲の立体描画、熱の揺らぎなどは、上記が実機で成立した後の候補に残す。

小さい反射が点滅に見える場合は、反射の幅・強さや遠距離の材質を見直す。静止画の鋭い光沢だけを合格条件にしない。

### 見送りの扱い

飛行終了時の急な消失が観察の余韻を壊す場合は、退場範囲・時刻を飛行計画として検討する。共通の便の終了を端末ごとに勝手に延長せず、音が届く時間も含めて設計する。この変更は初回の照明比較へ混ぜない。

## 5. 機体制作の進め方

**最初は現行のコード生成モデルで、光と見える形の改善効果を確認する。** 改善が必要な部位を絞った後、Blenderで制作するかを決める。

- コード生成で比較する対象：胴体の断面・曲率、翼の厚みと輪郭、エンジンの縁と吸気口、材質。
- Blenderを検討する条件：曲面や部品の接合をコードだけで調整すると手間が大きい、塗装・汚れ・部品配置を視覚的に作りたい、近い距離でも見る用途が固まる。
- 導入時は1部品または1機を比較対象にする。単位m、前方+Z／上+Y／右+X、機体中心と取り付け位置、胴体長・翼幅・双発／四発への対応を決める。
- 新モデルでも、画面とレシピから寸法・エンジン数を変える体験を維持する。固定モデルの追加と、自由に作れる機体の改善を同じ完了条件にしない。
- 模様で表す微細な凹凸と、輪郭に影響する形状を分ける。距離別の簡略化で、シルエットや光沢が急に変わらないか確認する。

## 6. 品質を確かめる比較手順

### 同じ条件で比較する

- 同一の機体寸法・航路・シード・速度・開始時刻・観測位置を保存する。音量、本体の音量、視線の向き、表示設定も記録する。
- 比較用の1機で、接近・側面がよく見える区間・下面が見える区間・遠ざかりを観察する。これは開発用の比較条件で、演目作成を利用者へ要求するものではない。
- 第1比較は現行／光の整合のみ、第2比較は環境反射と材質、第3比較は形状という順番で、違いの理由を追えるようにする。
- 通常の地上視点と倍率を主評価にする。拡大や近接プレビューは原因調査にも使う。晴天だけに調整が偏らないよう、曇天も比較条件に置く。
- マルチは同じ飛行条件で、個人の視点・音量・描画負荷設定を変えても飛行予定がずれないことを確認する。

### 機械で確認すること／人が判断すること

| 種類 | 記録すること | この記録だけでは言えないこと |
| --- | --- | --- |
| 描画 | 便・時刻・観測位置、表示状態、機体の画面内サイズ、細部表示、両眼の画像・動画 | 魅力や見惚れる感覚 |
| 安定性 | XRフレーム間隔、途切れ、細部境界の変化、ちらつき、アセット読込 | 頭を動かしたときの快適さの全評価 |
| 音 | 到来時刻、音源位置、発音数、出力ピーク、比較時の音量 | 厚み・気持ちよさ・疲れの程度 |
| 試遊 | 「どの瞬間を見ていたか」「もう一度見たいか／なぜか」「気が散った箇所」 | 他の人や展示会全体でも同じ評価になること |

好みの数値を先に一つへ集約せず、どの瞬間が良くなったかを残す。初回はユーザー自身の評価を基準に方向を合わせ、その後、初見の人でも説明なしに楽しめるかを見る。頭を動かした回数や滞在時間だけで「見惚れた」と判定しない。

### 最初の採用条件案

1. **見える**：通常の観察条件で改善箇所を実機で確認できる。見えない場合は距離・角度・状態・画素・背景のどこで失われたか記録する。
2. **魅力がある**：本人が改善した場面を具体的に挙げられ、もう一度見たい理由につながる。
3. **続けて見られる**：ちらつき、小刻みな姿勢変化、音切れ、UIの遮りが新たに増えない。
4. **動作が成立する**：Quest 3で継続試遊し、フレーム間隔・熱による変化・音・共同操作の結果を記録する。

## 7. Questでの負荷と描画の仕様境界

- 初期試作の対象はQuest 3本体スピーカー・単機。既存の単体3機と共有2端末でも回帰を確認する。
- 最初に基準版を測り、試遊時の更新頻度から1フレームの時間`B = 1000 / Hz`を求める。例として72Hzなら約13.9ms、90Hzなら約11.1ms。採用する更新頻度は実機で確認し、ここでは固定しない。
- 暫定の比較目安は、継続飛行時のフレーム間隔p95が`1.25B`以内、`2B`超の割合が1%未満。これは開発側の検証案で、未測定・受入未合意。基準版が満たさない場合も品質完了とせず、原因と目標を見直す。
- 既存の`frameMsP50/P95`はXRフレーム間隔で、GPU処理時間そのものではない。直近600フレームの集計のため、10分程度の継続試遊を評価する記録方法は追加が必要。メニュー表示・追跡停止・ロードを飛行中の集計と区別する。
- 描画命令数、三角形数、テクスチャ量、初回読込量を変更前後で記録する。XRの左右眼・各描画処理を含む値か確認してから予算化する。三角形数だけで速度を判断しない。
- 環境反射は固定設定から作って再利用する方式を第一候補にする。毎フレームの生成は初回条件にしない。画質設定では周辺風景や微細な模様から負荷を調整し、機体の外形・滑らかな姿勢・方向を持つ音を優先する。
- 両眼の投影と実際の描画領域から画面内サイズを確認する。PCの画角やキャンバスの大きさを、そのままQuestの解像度とみなさない。

## 8. マルチ・ARとの関係

太陽・空・機体外観のように同じ空を作る条件と、端末ごとの解像度・細部省略を分ける。将来共有する外観設定は、保存形式・ルームの版・既存の招待との互換性を決めてから追加する。描画品質の違いで機体サイズ・航路・開始時刻・音の伝播を変えない。

基本ARでは仮想背景を外しても機体の面が読めるかを別に確認する。VR用の太陽設定が現実の照明と自動一致する機能は現行にない。まず明るい／暗い現実背景での視認性を検証し、照明合わせの手動調整を候補にする。会場の校正・ブース案内は[ARの2モード](ar-modes.md)で扱う。

## 9. 品質改善の4つの作業単位（実機受入 0/4）

| 順番 | 作業 | 次へ進む判断 |
| --- | --- | --- |
| 1 | 基準の飛行・視点・音を保存し、見えない原因とQuest負荷を記録 | 比較する条件と、最初に直す箇所が説明できる |
| 2 | 太陽の整合、環境反射、部位の材質を小さく比較 | 通常距離で側面・下面の違いが見え、ちらつきと負荷が許容できる |
| 3 | 必要な輪郭・接合部・空の背景を改善。Blender採否を決める | 近接だけでなく地上からも効果があり、機体編集が維持される |
| 4 | 音と見送り、操作表示を合わせて通し試遊する | 具体的な「見惚れた瞬間」と実機の動作記録が残る |

この4分割は品質改善のための検証単位。全体6段階やマルチ試作4/5を変更するものではない。ARの搭載順とマルチの実機確認は、それぞれの進捗で管理する。

## 10. v0.8.1の実装記録

### 今回の変更

- **太陽・空・照明**：`SkyEnvironment.tsx`で方向を一元化。太陽の円盤、空の明暗、控えめな高層の雲の表現をコードで生成する。観察位置が変わっても空の方向を保つ。
- **環境反射と材質**：同じ空から128pxの環境マップを起動時に一度作り再利用。白い塗装・翼・金属の吸気口・ガラスの材質を分けた。外部HDR画像やモデルの読み込みは追加していない。
- **機体**：胴体と上部の膨らみを連続した曲面にし、機首窓を表面に沿わせた。主翼・尾翼は厚みと丸い前縁を持ち、主翼には上反角を付けた。エンジンは外殻・金属リップ・内部・後部ノズルを持つ。
- **編集との両立**：長さ50〜85m、翼幅45〜85m、双発／四発を維持。寸法変更は既存形状の変形で処理。エンジンの同じ部品をまとめて描画する。形状生成を別ファイルへ分け、今後は部品単位でも改善できる。
- **小さい細部**：窓を実効距離700〜1500mで徐々に薄くする。PCの拡大時には画角補正する。吸気口と操縦席は遠くでも外形を維持する。これによるQuest実機のちらつき改善は未確認。

飛行姿勢・航路・時刻・音の合成・共有の保存形式は変更していない。今回は晴天の一条件。天候切替、AR、実世界の照明推定、音の余韻・退場、UI表示の変更は後続。Blenderはまだ使用していない。

### 再現比較と負荷の記録

`npm run test:quality`をViteへ向けて実行する。`QUALITY_OUTPUT`で保存先を指定できる。実飛行の比較は同じ航路・観測位置・経過23.5／33.5／45.5秒、距離約500／864／1516m。近接確認は別のカメラで、双発・四発、下面、最短・最長と狭い・広い翼を確認する。

保存先: `output/quality-baseline`（更新前）、`output/quality-light`（照明のみ）、`output/quality-final`（形状と描画の更新後）。各`result.json`にレシピ・位置・向き・状態・描画カウントを保存。静止画に加え、飛行・VR操作の回帰を別のブラウザ検証で確認する。

確認結果: 自動テスト92件、PC操作20項目、機体編集12項目、配布版VR模擬23項目、共有操作はローカル・公開版とも10項目が成功。型確認とビルドも通過。これらは実機での美しさ・負荷の判定とは分ける。

| PCの同一飛行条件 | 更新前 | v0.8.1 |
| --- | --- | --- |
| 約500m・描画命令 | 77 | 67 |
| 約500m・三角形 | 9,188 | 21,780 |
| 約864m・描画命令 | 55 | 45 |
| 約864m・三角形 | 7,164 | 19,756 |
| 約1516m・描画命令 | 56 | 45 |
| 約1516m・三角形 | 7,388 | 15,820 |
| 登録された形状 / テクスチャ | 77 / 1 | 66 / 2 |

これらはPCの単眼描画・シーン全体のカウントで、GPU時間やQuestの速度ではない。曲面のため三角形は増えたが、エンジンの一括描画で命令は減った。環境マップ生成中の一時的な負荷を表す数値でもない。近接モデル確認は背景が異なるため、この負荷比較には使わない。

### 残る判断

| 作業単位 | 今回進んだこと | 残り |
| --- | --- | --- |
| 1 基準の記録 | PCで同じ飛行と観測位置を再現、更新前後を保存 | Questの実効解像度・10分程度の動作測定 |
| 2 光・材質 | コード実装とPCの比較を実施 | Questの両眼で光・反射・ちらつきを評価 |
| 3 形・空 | コード生成モデルを更新し、寸法変更を確認 | 通常距離で魅力が届くか、Blenderが必要な部位の判断 |
| 4 音・余韻・表示 | 今回の変更対象には含めていない | 前3項目の実機評価を踏まえて着手 |

コードで見た目を改善したことと、「見惚れる」体験の受入は別。**4単位の実機受入は0/4**のまま、1〜3の実装・PC検証が進んだ状態とする。

## 技術の根拠

2026-09-16に公式資料を確認。採用効果・Quest対応を保証するものではなく、実験の根拠として使う。

- [Three.js MeshStandardMaterial](https://threejs.org/docs/pages/MeshStandardMaterial.html)：粗さ・金属度・環境マップによる材質。環境反射を加える比較と、部位の光沢を分ける方針の参考。
- [Three.js WebXRManager](https://threejs.org/docs/pages/WebXRManager.html)：XRは各ビューにカメラを持つ。描画倍率・foveationの設定と、実機の結果を分けて確認する。
- [MDN XRView.projectionMatrix](https://developer.mozilla.org/en-US/docs/Web/API/XRView/projectionMatrix)：ビューごとの投影に基づいて、機体の画面内サイズを評価する。
