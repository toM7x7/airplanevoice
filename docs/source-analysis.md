## 引き継ぐ体験の原則

- 描いた線は飛行中に消える。飛行機へ視線を向けられる空にする。
- 発音した過去の場所から音が届く。現在の機体位置へ音源を貼り付けない。
- 航路は機体に合わせて滑らかに整える。極端な入力にも使える結果を返す。
- 外部AIがなくても、描く・飛ぶ・聴く・もう一周が成立する。
- 画面操作、技術上の合格、実際の体験評価を分けて記録する。

## 今回の解釈と選択

### 最初の到達点

青写真PoC 0 / 仕様書S0に相当する、デスクトップの現象検証版を先に作る。単体のWebアプリとして実際に触り、機体の大きさ、空間、音のずれ、再周回の感覚を判断できる状態にする。

### 音とフェーズ

発音イベントは飛行中にも順次到来する。FLYと音到来処理は並行し、ARRIVALは周回が終わった後に残りの音を受け取る期間とした。周回の終わりまで音を一律に待たせない。

### 機体と航路

初期は架空の四発機の固定メッシュを使用。旋回や視点に対して翼とエンジンがどう見えるかを確かめる。航路には周期的なB-splineを使い、終端と始点のつながりを滑らかにする。必要な旋回半径に応じて航路を広げる。極端に鋭い線は標準旋回へ置き換え、編集画面で通知する。

### 音と周回差分

音色はローカル合成の仮素材。到来時刻、方向、距離減衰、Dopplerの動作確認に使う。次周の差分は低音層一つに限定し、航路の変化と音色の変化を混同しないようにした。

### アプリの構造

計算と画面を分ける目的は、このWebアプリ自体の保守と再現性の検証。別プラットフォーム用のアダプターや移行互換層は設けていない。

## 次に体験から判断する論点

1. 一周約90秒の旋回は長く眺めたい時間になるか。直線的な一度のフライバイを別の入口にするか。
2. 音航跡へ視線やポインターを向けたとき、音の層を解きほぐす操作は発見を増やすか。
3. 画面内の航路図から、空へ直接線を描く操作にすると、描く楽しさは増えるか。
4. 機体形状・光・実録音を磨いたとき、存在感はどこから最も増えるか。
5. 単体体験が成立した後に、独自の共有セッションやWebXRを導入する価値があるか。

これらは次の候補であり、実装済みや確定済みの扱いにはしない。
