# SOUND TRAIL — プロジェクトの方向

更新: 2026-09-15 / v0.3

この文書を、会話と試作から更新する現行方針とする。3冊のWordは原点を保存する基礎資料。資料内の指示例や初期案が、後から合意した方針を上書きすることはない。

## 作りたい体験

**音を手がかりに空を向き、飛行機を見つける。その空を、いずれは隣の人とも共有する。**

空を眺める余白、機体の存在感、あとから届くエンジン音を中核にする。自分で飛行を作る面白さと、誰かが飛ばした機体に気づく面白さを育てる。独立したWebサービスとして、必要な表現・エンジン・操作を選ぶ。

## ユーザーと確認済みの方向

| 決定 | 開発への反映 |
| --- | --- |
| 独自サービス・単体検証として作る | XRiftの制約、連携、移行互換性を前提にしない |
| Wordを基礎に、別の資料も更新しながら作る | 本書で現行方針を管理。原本は編集しない |
| 音の方向が気になり、向く瞬間が楽しかった | この発見を、説明や演出の量を決める基準にする |
| 複数Questで同じ空間に入り、同じものを共有したい | 共有飛行予定と観測者別音響を目標に設計する |
| AIは管制官のような案内・調整役 | 飛行の受付、予定・状況の案内、順番の提案を扱う |
| AR、機体・音・空の磨き込みに期待 | WebXR実機試作と、体験の質の改善を継続する |
| 機体を作る・航路を作る・飛ばして観察する | 画面操作とJSONを共通のレシピにする |
| 重さや慣性が感じられる滑らかな飛び方 | まず傾きがゆっくり追従する表現を試す |
| 通常はクラウド、会場からネットで接続 | 試遊版はGitHub Pages。独自ドメインは取らない。本番基盤は別途相談 |
| ローカルはフォールバック | 単体のオフライン再開を用意。ローカルAIは接続方法の設計に留める |
| 思いつきは実装とは別軸で残す | [思いつきメモ](idea-notes.md)へ蓄積し、採用前の案を実装予定に数えない |

「任意のところから離発着する」は発展させたい候補として記録する。地点を決める操作、必要な空間、離発着の表現は未確定。Blenderを使った部品制作、リアルタイム解説、QRでの入室も具体化候補。

## v0.3で触れるもの

- 「つくる実験室」で胴体・翼・エンジン数を変え、空で見る。
- A/Bの2地点、幅、高度、速度、シード、ゆらぎから航路を作る。離発着ではなく空中の通過点。
- 傾きの追従時間を調整し、曲がり方の印象を比べる。
- JSONレシピを編集・適用・書き出し。機体と航路は端末に保存する。
- 公開版を初回取得した後は、通信が切れても単体体験を再開する。

- PCブラウザで1〜3機を飛ばす。開始間隔は同時・8秒・16秒。
- 同じ編集航路をもとに、追加機は位置をずらした比較用航路を飛ぶ。
- 注目する1機を聴く／空全体を聴く。ほかの機体の音を残しながら、注目機を切り替える。
- オプションの管制字幕。準備、飛行開始、最初の音の到来、周回終了、全体終了を案内する。
- 各機の音到来が終わるまで待ってから、次の周回へ進む。

管制字幕は**定型文によるローカル実装**。外部AI、音声読み上げ、操縦指示、衝突回避は接続していない。複数機は1端末内の試作であり、複数人同期ではない。

## 独自エンジンを育てる単位

描画ライブラリやブラウザの標準機能を使いつつ、体験固有の判断と計算を自分たちのコードに持つ。詳細は[エンジン設計](engine-design.md)。

| 単位 | 担うこと | 現在 |
| --- | --- | --- |
| 航路・飛行 | 描いた線を解釈し、時刻から機体の姿勢を決める | 実装済み |
| 空域・運行 | 機体、航路、飛行開始時刻、進行状態をまとめる | ローカル3機まで |
| 音伝播 | 過去の発音点から、観測者に音が届く時刻を計算 | 近似モデルを実装 |
| 聴き方 | 機体別の響き、音の密度、聴取対象を調整 | 注目／全体を実装 |
| 管制・解説 | 状況の案内、飛行順の提案、音を聴く時間への配慮 | 状況字幕の土台 |
| 機体・空の表現 | 機体部品、材質、光、雲、距離感 | 寸法・配置を変える仮メッシュ、反復部品の一括描画、遠距離の細部省略 |
| 共有空間 | 部屋、共通時刻、参加・復帰、空間の位置合わせ | 未実装 |

空の表現や機体制作は、必要が出た時点で切り出す。まだ使わないエンジンの空フォルダは設けない。

## 次の段階と確かめること

順番は暫定。実際の体験結果で入れ替える。

1. **作って、飛ばして、また変える。** v0.3の機体・2地点航路・レシピで、この往復が楽しいかを試す。追従時間で重さを感じるか、同時／時間差・注目／全体でも「どっちにいる？」が残るかを確認。公開URLと単体の予備動作を検証する。
2. **1台のQuestで、その空に立つ。** 独立WebXR、頭の向きに追従する音、実機フレーム時間を確認。HTTPSの検証環境を用意し、VRから始めてARの支持機能を実機確認する。
3. **2台で同じ飛行を見る。** 部屋と共通時刻を導入。途中参加でも同じ機体を同じ時刻の位置に出す。音は各自の観測位置で別々に届く。切断・復帰を試す。
4. **現実の場所に、その空を重ねる。** QRによる同じ部屋への入口と、現実空間の原点・向き合わせを別々に検証。QRを読んだだけで空間が一致したとは扱わない。同室／遠隔の共有方式もここで選ぶ。
5. **飛ばし方を管制官と相談する。** 任意地点からの離発着、離発着順序、混雑への提案を検証。LLMは構造化した提案を出し、飛行エンジンが条件を確認して採用する。

機体の存在感、エンジンの音色、空の光は段階1以降も並行して磨く。最初の品質改善候補は、通過時の音の層、翼の陰影、近景と遠景の距離感。Blender導入は、メッシュや部品の制作目的が定まってから判断する。

## 管制官AIの役割

- 「どこから、どちらへ飛ばしたいか」を受け取り、飛行案にする。
- 現在の飛行予定を読み、次の開始時刻や順番を提案する。
- 見えている／聞こえている出来事を、実際のイベントに基づいて短く案内する。
- 音を聴く場面では発話を控える。実況の連続発話を前提にしない。

飛行位置を毎フレームAIで計算しない。AIの返答が遅れても、飛行と音の時刻は進む。返答には対象の便、予定の版、適用できる時刻を付け、古い案内や変更案は採用しない。これは今後の設計方針であり、現行の字幕にLLMの判断は含まれていない。

## 多くの機体が飛ぶときの考え方

1. **共有する予定で調整** — 開始間隔、飛行経路、同時飛行数。全員が見る空に反映される。
2. **各自の聴き方で調整** — 注目機、距離減衰、音量配分、同時発音数。ほかの参加者の設定を変更しない。
3. **管制案内で調整** — 次の発進を提案する／近接通過中は話さない。

「音を減らすほどよい」とは決めない。遠くの機体に気づける程度の背景音は残す。現在の最大3機と音量配分は、初回比較の値であり、完成仕様ではない。

## まだ決めないこと

- 対応Questの世代、必要同時人数、同室ARと遠隔共有の優先順。
- AIモデル・サービス・音声合成・課金方式。
- 本番の配信・共有サーバー、永続保存と利用分析の範囲、共有体験の公開時期。試遊版はGitHub Pagesを使用し、[本番環境の相談](production-options.md)でCloudflare・Vercel等を比較する。
- 離発着時の入力、空港の再現度、飛行性能の精度。

その段階の試作に必要になった時点で、選択肢と実機結果をもとに決める。
